# auth-from-scratch

A small, illustrated walkthrough of how modern authentication and single
sign-on (SSO) actually work under the hood — public/private key pairs,
signatures, JWTs, and the full OIDC-style login "dance" — built from the
primitives up, in Python, with a runnable toy web app at the end.

This repository doesn't teach you how to configure Okta or Auth0. It teaches
you what those services are doing for you, so that configuring them (or
reasoning about whether they're secure) stops feeling like trusting a black
box.

## Who this is for

Anyone comfortable reading Python who has used an SSO provider (Okta, Auth0,
Google/Microsoft sign-in, etc.) as a consumer or an administrator, but has
never seen the mechanics underneath — particularly the moment where a
public/private key pair turns into "you can trust this login."

## How the repository is organized

```
auth-from-scratch/
├── part1-foundations/       7 Jupyter notebooks, in order, building up
│                            from symmetric encryption to a full simulated
│                            SSO login flow
└── part2-web-app/           Two small Flask servers -- a toy Identity
```

### Part 1 — Foundations (start here)

Work through these in order; each one builds on the last.

| Notebook | What it covers |
|---|---|
| `01_symmetric_encryption.ipynb` | One shared key, both directions — and the problem it can't solve |
| `02_asymmetric_keypairs.ipynb` | Public/private key pairs; encrypt with public, decrypt with private |
| `03_hashing.ipynb` | One-way fingerprints; why passwords are stored hashed, salted, and slow |
| `04_digital_signatures.ipynb` | The flip: sign with the private key, verify with the public key — the actual foundation of trust |
| `05_building_a_jwt_by_hand.ipynb` | Constructing a JWT byte-by-byte, no libraries |
| `06_verifying_and_forging_jwts.ipynb` | Verifying a token correctly, then trying (and failing) to forge one |
| `07_simulated_oidc_dance.ipynb` | The full login choreography, in plain Python objects — Identity Provider, Relying Party, and the browser in between |

Run them with Jupyter:

```bash
pip install -r requirements.txt
jupyter notebook part1-foundations/
```

### Part 2 — A real (toy) web app

See [`part2-web-app/README.md`](part2-web-app/README.md) for instructions.

## How this maps onto Okta / Auth0 / real SSO

| In this repository | In a real deployment |
|---|---|
| Aegis ID (toy Identity Provider) | Okta, Auth0, Google, Microsoft Entra ID, etc. |
| Lighthouse Notes (toy Relying Party) | Your application — e.g. a service you host on your Raspberry Pi |
| The signed token exchanged between them | An OIDC ID token (a JWT) |
| "Only Aegis ID's private key can produce a valid signature" | The exact reason you can trust a login without your app ever seeing your password |

## What's intentionally simplified

This is a teaching tool, not a reference implementation. Each script also
carries these notes inline, but for visibility:

- Runs over plain HTTP on `localhost`, not HTTPS — a real deployment
  requires TLS end to end.
- No PKCE, nonce replay protection, consent screen, refresh tokens, or rate
  limiting.
- Signing keys are generated fresh in memory each time a server starts, and
  the user directory is two hardcoded accounts. A real Identity Provider's
  signing key is a long-lived, carefully protected secret, and its user
  store is persistent and access-controlled.
- No client secret or signed client assertion is used at the token endpoint.
- The on-page "process trace" is a teaching aid with no equivalent in a real
  protocol — real identity providers don't narrate themselves to the browser.

Do not deploy any part of this repository as an actual authentication
system.
